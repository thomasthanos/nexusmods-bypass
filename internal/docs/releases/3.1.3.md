# 3.1.3 — Download popup conflict fix

Chrome can return “Another extension has disabled the download UI” when this extension restores the download popup. Chromium has already removed our restriction at that point; another extension still wants the popup hidden. This expected response no longer generates a false `background_error` or an automatic Discord report.

The extension remembers that its own restriction was released and clears its restoration alarm. Repeated queue events do not repeat that request. Later collection runs can still hide and release the popup normally, without overriding another extension's choice. Unexpected failures remain reportable and retryable. Download security checks and file transfers are unchanged.

Regression tests reproduce the original failure and cover idle restoration, collection completion, a restarted worker, alarm cleanup, subsequent collections, unexpected errors and browsers without `downloads.setUiOptions`. A Chromium integration test loads a second extension that hides the real download UI, verifies the native rejection, then checks that collection completion releases our restriction and clears its alarm without recording a background error.

Chrome and Firefox packages use 3.1.3 with the same permissions. Update the installed extension to receive this fix. Older versions may still send the previous report; existing Discord messages are unchanged.

The Cloudflare relay remains on its verified 3.1.2 deployment; no server change is needed for this client-side API response. No live Discord test messages were sent.

Technical basis: <a href="https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/extensions/api/downloads/downloads_api.cc"><kbd>Chromium downloads API implementation</kbd></a>, `DownloadsSetUiOptionsFunction::Run` applies `MaybeSetUiEnabled` before returning `kUiDisabled` when another extension keeps the UI disabled.
